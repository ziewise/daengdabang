## 1. 목표

1. 홈, 전체 추천, 펫렌즈 후속 화면이 하나의 추천 계약과 엔진을 사용한다.
2. 다견 회원이 추천 대상 반려견을 직접 선택할 수 있다.
3. 각 상품에 사람이 이해할 수 있는 추천 이유와 주의 문구를 제공한다.
4. 프로필, 펫렌즈, 향후 행동 신호의 사용 여부를 사용자가 관리할 수 있다.
5. 건강·알레르기·위험 신호는 광고 타기팅이 아니라 제외·억제·안내에 우선 사용한다.
6. 개인·건강 정보를 분석 이벤트에 싣지 않고도 추천 품질을 측정한다.
7. 기존 배포 기능을 유지하면서 기능 플래그로 단계적으로 전환한다.

## 2. 이번 범위에서 하지 않는 일

- 댕자랑 게시물의 사진·본문에서 성향이나 건강 정보를 추론해 상품을 자동 추천하지 않는다.

- 산책 메이트 위치 공유, 지역 실시간 혼잡도, 유기견 자동 점수화, 중고 결제·정산을 함께 구현하지 않는다.
- 상품 카탈로그의 권위 저장소가 프런트에 있는 동안 동일한 랭킹 로직을 백엔드에 복제하지 않는다.
- 현재 `popularity` 합성값을 판매량이나 실제 인기도라고 표시하지 않는다.

## 6. 신호 사용 정책

### 6.1 기본 사용 가능

아래 값은 회원이 직접 등록·수정한 프로필이고 맞춤 추천 목적이 고지된 경우에만 사용한다.

| 신호 | 용도 | 제한 |
|---|---|---|
| 반려견 크기 | 상품 대상 크기 필터·가중치 | 실제 상품 사이즈표가 없으면 적합을 단정하지 않음 |
| 생애단계 | 퍼피/성견/시니어 용도 필터 | `age` 자유 문자열보다 `lifeStage` 우선 |
| 활동량 | 산책·놀이·휴식 카테고리 가중치 | 건강 상태로 해석하지 않음 |
| 모질 길이 | 브러싱·목욕·관리 용도 가중치 | 피부 질환으로 추론하지 않음 |
| 회원 확인 견종 | 상품 대상 설명 보조 | 모델 추정 견종보다 회원 확인값 우선 |
| 회원이 선택한 관심사 | 카테고리 가중치 | 허용된 선택지 코드만 사용, 자유 문장 분석 금지 |
| 체중 | 실측이 필요한 착용 상품의 후보 축소 | 정확한 사이즈 보장 문구 금지, 분석 이벤트 전송 금지 |

### 6.2 별도 사용 허용이 필요한 신호

| 신호 | 기본값 | 허용 시 용도 | 금지 용도 |
|---|---|---|---|
| 펫렌즈 추천 신호 | 검증 가능한 기존 동의가 없으면 끔 | 허용 코드로 변환한 뒤 카테고리 보조 | 원문 전체를 광고 타기팅에 사용 |
| 알레르기 | 회원이 명시적으로 등록한 경우에만 | 확인되지 않은 먹거리·성분 상품 제외 | “알레르기에 안전” 주장, 긍정 점수 부여 |
| 찜·검색·클릭·구매 | v1에서 끔 | 향후 별도 동의 후 개인화 | 현재 MVP 점수 입력 |
| 댕자랑 게시물 | v1에서 사용 금지 | 향후 게시물별 명시 동의가 있을 때만 검토 | 사진·본문에서 민감 정보 자동 추론 |

### 6.3 상품 추천 점수에 사용 금지

- 사진 원본, 영상 원본, 대화 원문, 게시물 원문
- 정확한 위치, 주소, 연락처, 회원 이름·이메일·전화번호
- 모델이 추정한 질환, 통증, 응급도, 위험 플래그
- 성별·중성화 여부처럼 현재 카탈로그 적합성과 근거가 없는 값
- 운영자가 검증하지 않은 외부 리뷰 문장의 건강 효능 주장
- 합성 `popularity` 값을 판매량·인기 증거로 사용하는 행위

### 6.4 안전 우선 규칙

1. 긴급 또는 당일 진료 확인 신호가 있으면 건강 안내를 먼저 표시한다.
2. 이 경우 먹거리·영양제 추천은 기본 억제한다.
3. 위험 신호는 특정 상품의 점수를 올리지 않는다.
4. 알레르기 정보가 있으나 상품 성분 데이터가 검증되지 않았으면 해당 먹거리 상품을 제외한다.
5. 착용 제품은 실제 체중·가슴둘레·목둘레 확인 전 사이즈 적합을 확정하지 않는다.
6. 추천 결과는 수의학적 진단이나 처방이 아니라는 안내를 유지한다.

### 계약 원칙

- 원문 자유 텍스트는 `RecommendationContext`에 넣지 않는다.
- 신호 정규화기는 허용 목록에 없는 값을 버린다.
- UI에는 숫자 점수를 노출하지 않는다.
- 추천 이유는 실제 점수에 사용된 코드로만 생성한다.
- `petProfileId`는 화면 상태와 인증 API에만 사용하고 공개 분석 이벤트에 전송하지 않는다.
- 엔진 버전을 결과와 이벤트에 남겨 롤백·비교가 가능하게 한다.

## 8. 랭킹 파이프라인

### 8.1 1단계: 상품 자격 하드 필터

아래 중 하나라도 만족하지 못하면 점수 계산 전에 제외한다.

- `recommendable === true`
- 유효한 오프셋 포함 ISO 시각으로 운영자 검수 완료
- 가격이 0 이상이고 표시 가능한 상태
- 이미지·상품 링크 등 카드 필수 데이터 존재
- `availability === "available"`
- 안전 억제 대상 카테고리가 아님
- 알레르기 제외 조건과 충돌하지 않음

상품 타입과 공개 카탈로그에는 다음 최소 운영 필드를 사용한다. 필드는 이전 카탈로그와의 읽기 호환을 위해
선택형이지만, 누락값은 추천 허용으로 승격하지 않는다.

```ts
type RecommendationCatalogPolicy = {
    recommendable?: boolean; // true만 추천 허용, 누락/false는 차단
    availability?: "available" | "sold_out" | "discontinued" | "unknown";
    operatorReviewedAt?: string; // 오프셋 포함 ISO date-time만 인정
    allergenTags?: string[]; // 운영자 검증 데이터가 있을 때만
};
```

`availability: "unknown"`, `sold_out`, `discontinued`는 카테고리와 무관하게 추천 후보에서 제외한다.
관리자에서 세 필드를 검수해 저장하면 관리자 `data/products.json`과 자사몰 `lib/catalog/raw.json`에 같은 값이 반영된다.

### 8.2 2단계: 적합도 점수

- 회원이 직접 선택한 관심사와 명확한 상품 용도 일치에 가장 높은 가중치를 둔다.
- 크기·생애단계·활동량·모질은 보조 가중치다.
- 펫렌즈 신호는 동의가 있고 허용 코드로 변환된 경우에만 보조 가중치를 준다.
- 실제 판매량이 아닌 `popularity` 합성값은 개인화 점수에서 제거한다.
- 동점 정렬은 운영자 검수 상태, 카테고리 다양성, 상품 ID의 안정 정렬 순으로 결정한다.

### 8.3 3단계: 다양화

- 홈 6개, 전체 추천 기본 12개를 반환한다.
- 홈에서는 동일 하위 카테고리를 최대 2개로 제한한다.
- 전체 추천에서는 상위 이유별 섹션을 제공하되 같은 상품을 중복 노출하지 않는다.
- 적합 후보가 부족하면 운영자 편집 추천으로 채우고 `editorial_fallback`을 명시한다.

### 8.4 4단계: 추천 이유

사용자 문구 예시는 다음처럼 짧고 검증 가능해야 한다.

- `활동량이 높은 아이의 산책 관심사와 맞아요.`
- `등록한 장모 관리 관심사를 반영했어요.`
- `착용 전 실측 확인이 필요한 상품이에요.`
- `개인화 후보가 부족해 댕다방 편집 추천을 함께 보여드려요.`

질환·효능·치료·예방을 단정하는 문구는 생성하지 않는다.

## 9. 반려견 선택 규칙

현재처럼 최근 분석된 반려견을 무조건 우선하지 않는다.

우선순위는 다음과 같다.

1. 사용자가 추천 화면에서 명시적으로 선택한 반려견
2. 서버 추천 설정의 `selectedPetProfileId`
3. 현재 회원 프로필 목록의 첫 번째 항목

최근 펫렌즈 분석 시각은 추천 신호의 최신성 판단에만 쓰고, 대상 반려견 자동 변경에는 쓰지 않는다.

반려견이 두 마리 이상이면 홈 추천 제목 옆과 전체 추천 상단에 선택기를 표시한다. 선택 변경은 추천 설정 API에 저장하되 분석 이벤트에는 프로필 ID나 이름을 보내지 않는다.

## 10. 사용자 화면 설계

### 10.1 홈

- 기존 `우리 아이 맞춤 추천` 위치를 유지한다.
- 다견 회원에게 반려견 선택기를 추가한다.
- 상품 카드에 한 줄 추천 이유를 표시한다.
- `왜 추천했나요?`를 열면 사용한 신호 그룹과 수정 경로를 보여준다.
- `맞춤 추천 전체 보기`는 실제 동일 반려견의 동일 엔진 결과로 연결한다.
- 추천이 꺼져 있으면 개인화 상품 대신 `댕다방 추천 셀렉트`와 켜기 링크를 표시한다.

### 10.2 `/recommendations`

- 서버 컴포넌트의 고정 목록을 회원 상태를 읽는 클라이언트 화면으로 교체한다.
- 비로그인: 편집 추천과 로그인 안내
- 로그인·반려견 없음: 프로필 등록 안내와 편집 추천
- 로그인·추천 켜짐: 선택 반려견의 개인화 결과, 이유별 섹션, 데이터 관리 링크
- 추천 꺼짐: 편집 추천만 표시
- 펫렌즈 동의 꺼짐: 프로필 기반 추천은 유지하고 `profile_only`로 표시

### 10.3 마이페이지 `추천 데이터 관리`

다음 제어를 제공한다.

- 맞춤 추천 전체 켜기/끄기
- 프로필 정보 활용 상태 확인
- 펫렌즈 분석 신호 활용 켜기/끄기
- 행동 데이터 활용: `준비 중`, 기본 꺼짐
- 기본 추천 반려견 선택
- 사용 중인 신호 그룹 확인
- 프로필 수정, 펫렌즈 결과 삭제 경로

설정을 꺼도 회원가입, 일반 쇼핑, 편집 추천은 계속 사용할 수 있어야 한다.

## 11. DB와 API 변경

### 11.1 신규 테이블 권장

`raw_analysis` 안에 동의를 넣지 않고 별도 테이블을 만든다.

```text
recommendation_preferences
- user_id PK/FK users.id ON DELETE CASCADE
- enabled boolean NOT NULL default true
- profile_signals_enabled boolean NOT NULL default true
- petlens_signals_enabled boolean NOT NULL default false
- behavior_signals_enabled boolean NOT NULL default false
- selected_pet_profile_id FK pet_profiles.id nullable ON DELETE SET NULL
- consent_version varchar(40) NOT NULL
- consent_source varchar(40) NOT NULL
- created_at timestamptz NOT NULL
- updated_at timestamptz NOT NULL
```

### 11.2 기존 회원 마이그레이션

- `enabled=true`, `profile_signals_enabled=true`는 회원이 직접 등록한 프로필의 기존 고지 범위 안에서 유지한다.
- 현재 가입 화면의 PetLens 선택 동의는 클라이언트에서 프로필 저장 여부를 제한할 뿐, 가입 API 요청과 서버 회원 레코드에 동의 버전·시각이 저장되지 않는다.
- 따라서 기존 회원의 `petlens_signals_enabled`는 전부 `false`로 이관하고 UI에서 새 버전 동의를 다시 받는다. PetLens 프로필이나 분석 결과가 존재한다는 사실만으로 동의를 추정하지 않는다.
- `behavior_signals_enabled`는 전원 `false`다.
- 삭제된 반려견을 가리키는 `selected_pet_profile_id`는 `NULL`로 정리한다.

### 11.3 API

```text
GET /api/v1/recommendation-preferences
PUT /api/v1/recommendation-preferences
```

`PUT`은 인증 회원 본인만 수정할 수 있고, `selectedPetProfileId`가 본인 소유인지 검증해야 한다. 응답은 변경된 설정과 동의 버전만 반환하며 프로필·펫렌즈 원문을 포함하지 않는다.

v1에는 `/api/v1/recommendations`를 추가하지 않는다. 현재 상품 카탈로그와 랭킹 로직이 자사몰 저장소에 있으므로 백엔드 복제는 불일치 위험이 더 크다. 카탈로그가 서버 권위 데이터로 이동하는 시점에 추천 API 전환을 별도 결정한다.

## 12. 분석 이벤트

### 12.1 신규 이벤트

프런트 `StorefrontEventName`, API `StorefrontEventName`, `PUBLIC_ANALYTICS_EVENT_TYPES`, 메타데이터 정제기를 한 변경 단위로 수정한다.

| 이벤트 | 발생 시점 |
|---|---|
| `recommendation_impression` | 추천 묶음이 실제 화면에 노출됨 |

| `recommendation_empty` | 필터 후 표시 가능한 결과 없음 |

- `engineVersion`
- `surface`
- `mode`

- `rank`
- `resultCount`
- `sourceSet`: `profile`, `profile+petlens`, `editorial`

### 12.3 전송 금지 메타데이터

- `petProfileId`, 반려견 이름, 견종, 나이, 체중, 알레르기
- 펫렌즈 신호 코드·원문, 위험·응급·질환 정보
- 추천 이유 전체 문장
- 회원 식별자, 이메일, 전화번호, 주소
- 사진·영상·채팅·게시물 원문

### 12.4 핵심 지표

- 추천 노출 대비 상품 클릭률
- 홈에서 전체 추천으로 이어진 비율
- 추천 이유 열기 비율
- 관심 없음/숨기기 비율
- 추천 결과 없음 비율
- 세션 내 추천 클릭 후 장바구니 진입률
- `profile_only`와 `profile+petlens`의 품질 차이

전환율만으로 품질을 판단하지 않고 숨김률, 빈 결과, 이유 확인, 안전 억제 회귀를 함께 본다.

### 1단계: 내부 검수

- 기능 플래그 아래 관리자와 지정 테스트 계정에만 새 엔진을 노출한다.
- 다견 선택, 추천 이유, 안전 억제, 빈 결과를 검수한다.

### 2단계: 홈 전환

- 홈 6개 추천만 새 엔진으로 전환한다.
- 클릭률보다 오류율·숨김률·안전 억제 실패를 먼저 본다.

### 3단계: 전체 추천과 데이터 관리

- `/recommendations`와 마이페이지 설정을 공개한다.
- 홈과 전체 페이지의 선택 반려견·엔진 버전·결과가 일치하는지 확인한다.

### 4단계: 관리자 집계

- 익명 추천 퍼널과 합성 시나리오 검수를 관리자에 연결한다.
- 안정화 후 기존 호환 래퍼 제거 여부를 결정한다.

## 16. 기능 플래그와 롤백

- `NEXT_PUBLIC_RECOMMENDATION_V1_ENGINE`: 새 순수 엔진 사용
- `NEXT_PUBLIC_RECOMMENDATION_V1_FULL_PAGE`: 개인화 전체 추천 페이지 사용
- `NEXT_PUBLIC_RECOMMENDATION_V1_PREFERENCES`: 사용자 설정 API/UI 사용
- `NEXT_PUBLIC_RECOMMENDATION_V1_ANALYTICS`: 신규 분석 이벤트 사용

> 구현 상태 (2026-08-13): 완료, 미배포. `lib/recommendation/feature-flags.ts`가 명시적인
> `1/true/yes/on`만 활성화하며 값이 없거나 잘못되면 모두 꺼진다. GitHub Pages 워크플로도 네 저장소
> 변수의 기본값을 `false`로 고정한다. 홈 개인화는 엔진+설정, 전체 페이지 개인화는 엔진+설정+전체
> 페이지가 모두 켜져야 작동한다. 설정 플래그가 꺼지면 설정 API 요청과 마이페이지 메뉴가 닫히고,
> 분석 플래그가 꺼져도 상품 숨김 UI는 유지되지만 추천 이벤트는 전송하지 않는다. 엔진이 꺼진
> 호환 경로는 회원 정보를 사용하지 않는 편집 추천으로 되돌아간다.

각 플래그는 독립적으로 끌 수 있다. 단, 정적 export의 `NEXT_PUBLIC_` 값은 빌드 시점에 고정되므로
저장소 변수를 변경한 뒤 GitHub Pages 워크플로를 다시 실행해야 실서비스에 반영된다. DB에 저장된
추천 설정은 롤백 시 삭제하지 않는다.

## 17. 테스트 기준

### 단위 테스트

- 허용되지 않은 펫렌즈 문장이 신호 코드로 들어가지 않음
- 회원 확인 견종이 모델 추정 견종보다 우선함
- 알레르기와 성분 미검증 식품이 함께 있으면 식품 후보 제외
- 긴급 관리 신호가 상품 점수를 올리지 않고 먹거리·영양제를 억제함
- 펫렌즈 사용이 꺼지면 `profile_only` 결과 생성
- 추천 전체 꺼짐이면 `disabled`와 편집 추천 대체
- 동일 입력과 엔진 버전에서 정렬이 결정적임
- 카테고리 다양화 한도 준수

### API 테스트

- 비로그인 접근 거부
- 다른 회원의 반려견을 기본값으로 설정할 수 없음
- 삭제된 반려견 선택값 정리
- 동의 버전과 변경 시각 보존
- `rawAnalysis`가 추천 설정 API 응답에 포함되지 않음

### UI 테스트

- 다견 선택 변경 후 홈과 전체 추천의 대상 일치
- 추천 이유가 실제 이유 코드와 일치
- 추천 끄기 후 개인화 상품 미노출
- 비로그인·프로필 없음·펫렌즈 꺼짐·빈 결과 상태
- 키보드로 선택기와 이유 패널 사용 가능

### 분석 보안 테스트

- 프런트와 API 이벤트 이름 허용 목록 일치
- 허용하지 않은 메타데이터 키 제거
- 반려견 이름·ID·견종·체중·알레르기·건강 문구 미전송
- 추천 이벤트 실패가 쇼핑 흐름을 막지 않음

## 18. MVP 완료 기준

- 홈과 `/recommendations`가 같은 선택 반려견과 같은 엔진 결과를 사용한다.
- 다견 회원이 추천 대상을 직접 선택하고 재접속 후 선택이 유지된다.
- 모든 개인화 상품에 최소 한 개의 실제 추천 이유가 있다.
- 펫렌즈 신호 사용을 끄거나 맞춤 추천 전체를 끌 수 있다.
- 건강 위험 신호가 긍정 타기팅에 사용되지 않는다.
- 품절·판매중단·검수 미완료 상품을 점수 계산 전에 하드 필터링한다.
- 신규 이벤트가 개인·건강 정보 없이 API에 수집되고 관리자에서 집계된다.
- 기능 플래그로 기존 흐름으로 되돌릴 수 있다.
- 기존 인트로, PWA, 브랜딩, 챗봇, 펫렌즈 저장 흐름의 회귀가 없다.

## 19. 확인 결과와 공개 전 선행 조건

### 확인 완료: 기존 PetLens 동의 증거 없음

- 가입 화면은 `agreePetLensPrivacy`를 확인하지만 `signupCustomer` 요청에는 필수 약관·개인정보 버전만 전달한다.
- API `SignupRequest`에도 PetLens 선택 동의 필드가 없다.
- 따라서 기존 PetLens 프로필의 존재를 추천 활용 동의 증거로 사용하지 않는다.
- 신규 추천 설정 API가 동의 버전·출처·변경 시각을 서버에 저장해야 한다.

### 확인 완료: 상품 운영 상태 권위와 안전한 초기 상태

- 자사몰 `lib/catalog/raw.json`을 배포 카탈로그 권위로 유지한다.
- 관리자 상품 편집기가 `recommendable`, `availability`, `operatorReviewedAt`을 입력하고, 배포 worker가 관리자
  `data/products.json`과 자사몰 권위 파일을 한 작업으로 갱신한다.
- 동기화 도구도 같은 세 필드를 보존하며, 누락·잘못된 값은 `false`, `unknown`, 미검수로 정규화한다.
- 추천 엔진은 추천 허용 true, 판매 가능, 유효한 운영자 검수 시각을 모두 만족해야만 상품을 후보로 사용한다.
- 기존 333개는 자동 승인하지 않았다. 현재 추천 가능 상품은 0개이며, 기능 플래그는 운영 검수 상품이 충분히
  확보될 때까지 기본 `false`를 유지한다.
- `available`은 관리자가 확인한 판매 상태이지 실시간 재고 연동 주장이 아니다. 식품 안전 적합이나 실재고도
  별도 검증 데이터 없이 주장하지 않는다.

### 2026-08-13 배포 준비 게이트

- 자사몰 전체 회귀 447개, TypeScript, 프로덕션 빌드 450개 경로가 현재 작업본에서 다시 통과했다.
  네 플래그를 모두 켠 출시 빌드와 모두 끈 기본 롤백 빌드가 각각 통과했다.
- API 추천 설정·분석·관리자 KPI 회귀 34개가 통과했다. 운영 DB는 무결성 `ok`, FK 오류 0이며 현재
  리비전은 `20260810_1030`, 배포할 코드 헤드는 `20260812_1200`이다.
- 관리자 콘솔 전체 회귀 100개, 인라인 스크립트·배포 worker·서비스워커 구문 검증,
  `index.html`·`sw.js`·`functions/api/admin/deploy-console.js`를 대상으로 한 GitHub 배포 도구 dry-run이 통과했다.
- 실제 배포와 커밋은 실행하지 않았다. DB 온라인 백업 → API 예약 작업 재시작/마이그레이션 →
  자사몰 → 관리자 콘솔 순서를 유지해야 한다.
- 전체 회원 공개 GO 전에는 관리자에서 충분한 상품을 개별 검수·저장하고, 공개 카탈로그에서 세 운영 필드와
  추천 가능 후보 수를 재확인한다. 현재 333개는 모두 안전한 차단 상태다.
- 네 독립 기능 플래그와 기본 비활성 배포값은 구현·회귀 완료했다. 실제 공개 단계에서는 저장소 변수를
  변경하고 새 정적 빌드를 배포해야 하며, 추천 후보 상품 검수가 충분히 끝나기 전에는 모두 `false`를 유지한다.
